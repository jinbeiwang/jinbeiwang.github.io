①本周 TL;DR

先给判断，后给证据。以下 5 条是编者按「对日常交付的影响」排出的取舍，不是原文结论。

  1. FDA 两份文件把「可核查性」同时推到设计端与数据端。11-11 发布 / 11-12 刊登《实体瘤早期 IND 试验方案建议》草案，把「SAP 需论证扩展队列最大样本量并含停止规则」「单臂不足以刻画 OS/PFS，时间-事件终点一般需随机研究」「RP2D 不应仅由 MTD 决定」写成设计期望；同日 RFI 就 RWD/RWE 患者级数据可及性征求意见，明确指出 FDA 目前不接受外部数据库链接、可复现的分析不能替代可核查的原始记录。判断：SAP 模板与数据溯源链要在方案阶段定死，别等锁库再补。
  2. CDISC 一致性核查本周最值得读的是「自我划边界」。JMIR 11-13 的实施成熟度模型自陈「概念框架、未经实证验证、部分数字来自单一机构或厂商分析」；R 包 coreval 11-11 上 CRAN，自陈「非 CDISC 关联、非 CORE 认证、非合格验证软件」，并把 $findings 与 $skipped 分开输出——空 findings 可能是规则根本没跑。判断：这类工具只能做开发期提示，不能替代合格验证系统；把「未检查」误读为「通过」是当前最现实的踩坑点。
  3. AI 侧三篇可复现预印本一致给出「有界」结论，没有颠覆。TrialDesignBench（617 个 I/II 期剂量探索试验）中 5 个前沿 LLM 无一匹配专家参考设计；Med Evidence Bench 在真实场景的证据可追溯分仅 0.182–0.447；SPARK 在缺测试用例场景下把代码生成共识验证提升最多 4.1%。判断：LLM 用于统计设计、证据检索、代码生成仍须人工复核与可核查基准，不宜按「颠覆式」叙事排能力计划。
  4. SAS 官方两篇博客给出一条 GxP 友好的架构线。11-10 的案例中既有 SAS 优化程序用 %include 原样复用、不重写建模逻辑，AI 只做前端与编排、人在环审批每次变更；11-12 的架构文明确「分析执行留在 SAS Viya，AI 助手只做协调；治理、审计、访问控制留在平台内，内部端点不暴露给 LLM」。判断：这比「让 AI 直接生成生产 SAS 代码」更接近可验证实践；本期补录的 6.4（PHUSE 上海 SDE 演讲资料）给出中文社区里同一架构线的不同实现，可对照着看。
  5. 监管与标准组织本周无重量级新标准发布。EMA CHMP 11 月会议是常规审评结果（7 个新药推荐、11 项适应症扩展），CDISC 官网 Newsroom 最新条目仍为 9 月，受控词表现行版本仍是 9-25 的 P62。判断：本周把精力放在草案意见期、现行 CT 版本核对与工具边界上，比追逐标题更划算。

1.1FDA 发布《实体瘤早期 IND 试验方案建议》草案指南（含明确统计设计口径）

2026-11-11 发布 / 11-12 刊登一手Federal Register 91 FR 72873草案
要点

由 FDA 肿瘤卓越中心（OCE）联合 CDER、CBER 起草，服务 HHS「Operation TrialBlazer」；覆盖首次人体试验的入排标准、剂量递增、扩展队列、RP2D 与伴随诊断。明确要求扩展队列的统计分析计划论证最大样本量并设置停止规则、单臂试验不足以充分刻画总生存或无进展生存（时间-事件终点一般需随机研究）、RP2D 应基于多个剂量水平与 PK/安全性/有效性 totality 而非最大耐受剂量单值；剂量递增幅度一般不超过 100%（小分子与 ADC）或半对数（多数其他生物制品），出现 ≥2 级不良事件后单患者加速滴定队列应转为至少 3 人。不适用于血液系统恶性肿瘤。评论截止 2027-01-11。

为何有用

这是本周对统计编程最直接的一份文件——「最大样本量依据」「停止规则」「单臂 vs 随机」都直接落到 SAP 章节与 TLF shell。若项目有 FIH / 剂量扩展，建议现在就用草案条目比对现有 SAP 模板，把样本量论证与期中停止规则的推导写成可复核文档；「提交时安全性数据不足可先只写剂量递增、扩展队列后续以修订案补充」一条会改变数据集版本与重跑策略。

1.2FDA 就 RWD/RWE 递交中的患者级数据可及性发布信息征询（RFI）

2026-11-12一手91 FR 72875RFI · 非指南
要点

FDA 就「含真实世界数据的药品/生物制品申请如何提交患者级数据」征求四类意见；文件明确 sponsor 常不拥有所用 RWD、无授权向 FDA 提交患者级记录，FDA 不能签署与其法定留存/披露义务冲突的数据使用协议，目前不接受指向外部数据库的链接；现行可行路径是第三方以 pre-IND 或 Type V DMF 提供数据、sponsor 出具授权信。文件特别要求保留「实际用于分析的提取物、派生历史与源数据关系」，并指出现有机制不改变 21 CFR 314.50 / 601.2 的义务。评论截止 2027-01-11；这是 RFI，不是指南、不是规则，不新增豁免。

为何有用

把「可复现分析」与「可核查记录」拆成两条独立依赖，正是临床统计编程最容易被忽视的分工。外对照 / RWE 项目在数据采购或方案锁库前应做一次可及性评估：逐数据源记录分析授权、患者级数据提供责任、源记录可供核查、留存与后续审阅条款四项，并保留提交版本与实际分析版本的对账链。把「可复现」当成「可递交」是常见误读。

3.3R 包 coreval 0.4.0 上 CRAN：在 R 内离线核查 CDISC Open Rules / CORE 规则

2026-11-11CRAN 一手作者声明非验证软件
要点

check_dataset() / check_study() 可在不离开 R 的环境下，用内置的 CORE 1.0（SDTM）与 CDISC Open Rules（SEND / TIG / USDM）规则检查一致性；可读取 .xpt、sas7bdat、CSV、Dataset-JSON，并在存在时读取 define.xml 与 USDM 研究设计文档；规则随包内置，不联网、不需 API Key、数据不出本机。输出 $findings（发现项，定位到具体行与变量）与 $skipped（未能检查的规则及原因）两张表，write_findings() 可导出 Excel / CSV。包页与参考手册明确声明：个人开源项目，与 CDISC、Verisian 无关联或背书，非 CORE 认证的一致性引擎、非合格/验证软件，「每个结果只是提示，不是裁决」，空 $findings 既可能是数据干净、也可能是规则从未运行。

为何有用

本周最贴合「可验证性 + 口径透明」的工具：把一致性检查前置到写 SDTM/ADaM 派生代码的当口，且 $skipped 的设计直接避免「没跑 = 通过」的误判。适合作为开发期快速自检或 CI 前置门禁；但绝不能替代已验证的核查系统与人工复核，也不宜把其输出作为递交依据。若引入，建议同时固定包版本与规则版本，并把 $skipped 一并归档留痕。

5.1JMIR Medical Informatics 发表「CDISC 实施成熟度模型（CIMM）」观点文章

2026-11-13PubMed 一手观点文章 · 未经实证验证
要点

JMIR Med Inform. 2026 Nov 13;14:e105990，doi 10.2196/105990，PMID 43024851，作者 A. 6.2Med Evidence Bench：把每条判分标准锚定到带版本原文片段的临床推理基准

2026-11-10 04:28 UTCarXiv 一手基准站点上线
要点

arXiv:2611.13562，山东大学等多机构团队，25 页 / 8 图 / 4 表。构建 1,536 个医师编制条目，分三层（指南知识、标准化临床场景、真实世界实验室场景），每条陈述医学主张的判分标准都链接到一个带版本的原文片段；10 个 LLM 的证据可追溯分（ETS）：指南知识 0.975–0.997、标准化场景 0.292–0.658、真实场景 0.182–0.447，且排名随层级变化。真实场景中「识别临床信息」（均值 0.770）显著高于「匹配证据」（0.165）与「形成建议」（0.160）。1,296 条准则级判定上，自动评分与三名医师多数票一致度 macro-F1 0.930（95% CI 0.915–0.945），证据应用类一致度更低。作者明确结论：中文材料上「能背指南」不保证患者特异性证据使用，且本研究不确立临床有效性。

为何有用

「每条断言链接到带版本的源文本片段」可迁移到统计编程文档自动化——SAP、TLF shell、define.xml 的计算方法说明都应能指回带版本的依据，而不是只给一句结论。量化警示也清楚：越接近真实场景，证据链越容易断；因此任何 AI 生成的统计文档，复核重点应放在「依据是否可指回源、版本是否一致」，而非语句是否流畅。

6.3SPARK：缺少测试用例时，用语义保持改写 + 共识验证提升代码生成可靠性

2026-11-10 00:29 UTCarXiv 一手CASCON 2026 已接收
要点

arXiv:2611.13401，Alireza Daghigh 等 6 人。针对「真实场景缺少测试用例、LLM 生成代码无法自动验证、只能人工校验」的问题，在共识验证（同时生成候选解与测试、按功能一致性评估）之上加入语义保持改写（复述、语法调整、函数重命名等），对每个改写描述生成一组代码与测试，用跨改写的一致性衡量解的质量；在 LiveCodeBench、BigCodeBench、DLBench 三个基准、o4-mini / DeepSeek-R1-Basic / Gemini-2.5-Pro 三个模型上，相比既有共识验证方法最多提升 4.1%。

为何有用

把「同一需求换几种说法、看多份实现是否收敛」形式化为可执行的验证信号，与临床编程里双编程 / 独立复核的思路同构，可作为 AI 辅助写代码时的轻量自检层。但这是在通用代码基准上的有限幅度改进，不能等同于 GxP 环境下的程序验证——生成的测试仍是模型生成、未经独立确认；提升幅度也说明该方向远未成熟。
